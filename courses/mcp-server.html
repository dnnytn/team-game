MCP Server Architecture

From “what is MCP?” to designing and deploying your own — local tool, multi-tenant service, and airgapped production — with inline quizzes after every segment.

Spec: MCP 2025-11-25 Transport: JSON-RPC 2.0 Length: 11 segments · ~20 quiz questions Audience: infra & platform engineers
Running example — ClusterOps MCP

ClusterOps is an internal MCP server at an airgapped bank. It exposes safe Kubernetes operations (list_pods, get_logs, restart_deployment, scale_deployment) to an AI assistant used by roughly 30 on-call SREs. Tools call the in-cluster API server; resources expose runbooks and current manifests; a prompt template drives incident triage. It sits behind an internal gateway that authenticates against the bank’s Keycloak. Zero outbound egress.

Every segment below has an In ClusterOps callout that shows how that concept lands in this one scenario, so the pieces compound instead of resetting each time.

1. Why MCP?

Every AI assistant worth using needs to reach beyond the chat box: read files, query databases, restart pods, open tickets. Without a standard, every assistant builds its own adapter for every tool. N assistants × M tools = N×M bespoke integrations, every one of which needs to be written, audited, updated, and monitored.

The Model Context Protocol collapses that into N + M. Each AI app learns MCP once. Each tool provider ships one MCP server. They speak a common protocol and pair freely. Anthropic published MCP in November 2024; the latest stable revision is 2025-11-25.

The analogy: LSP for AI tools

If you’ve worked with editors and language tooling, you already know the shape of this problem. Before the Language Server Protocol, every editor wrote bespoke Go support, Python support, Rust support. After LSP, gopls speaks LSP, and every editor that also speaks LSP inherits Go intelligence for free. MCP is the same move, one layer up: instead of editors ↔ languages, it’s AI hosts ↔ tools and data.

In ClusterOps

The bank has three places where SREs want to touch Kubernetes with an AI: the internal chat UI, the on-call engineer’s VS Code, and a command-line agent on jump hosts. Without MCP, the platform team would ship and maintain three k8s adapters — three places to patch when the API surface changes, three audit paths for Security. With MCP, they ship one ClusterOps server. All three AI surfaces are MCP clients and reach it the same way.

In the wild

GitHub’s official MCP server is the poster child for this collapse. Before it, Claude Desktop, Cursor, Zed, and Windsurf each had their own GitHub integrations. Now they all point at the same server and get identical behaviour. That’s the whole pitch in one bullet.

2. The three roles: Host, Client, Server

Every MCP deployment has exactly three roles. They sound interchangeable on first read, but the boundaries matter — especially for credentials.

Host

The application the user interacts with. Claude Desktop, VS Code with Copilot, an internal chat UI, an agent in a terminal. The host owns the user-facing surface, the consent prompts, the security policy, and the LLM itself. It decides which servers are allowed and hands user approval gates to each tool call.

Client

The host spins up one MCP client per server it wants to use. A client maintains a 1:1 connection with exactly one server and speaks JSON-RPC on that connection. A host with four servers has four clients running inside it. Clients are the protocol plumbing — the host delegates “call this tool” or “read this resource” to the right client.

Server

The process that actually exposes tools, resources, and prompts. It holds the backend credentials — the kubeconfig, the database password, the Jira API token — and translates MCP requests into real work. Servers can be local (launched as a subprocess over stdio) or remote (reached over HTTP).

In ClusterOps

The Host is the SRE’s internal chat UI (plus the LLM it embeds). The Client is a thin MCP adapter inside the host, dedicated to the ClusterOps connection. The Server is a container running in a dedicated namespace inside the cluster, mounted with a ServiceAccount that grants just enough RBAC to list pods, fetch logs, and restart deployments. The kubeconfig exists only on that pod. The host never sees it; the client never sees it; a compromise of the SRE’s laptop cannot exfiltrate it.

3. Protocol primitives

A server exposes three primary primitives. Knowing which is which determines who decides when they fire and what happens when they fail.

Tools — model-initiated, side-effectful

A tool is a named, schema-validated operation the LLM can choose to invoke. The host lists tools to the model via tools/list; the model replies “call restart_deployment with these arguments”; the host runs tools/call; the server does the work and returns a result. Tools can have side effects, so the host typically asks the user to approve each call. 

{
  "name": "restart_deployment",
  "description": "Perform a rolling restart of a Deployment by bumping its pod template annotation.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "deployment": { "type": "string", "description": "Deployment name" },
      "namespace":  { "type": "string", "description": "Namespace" }
    },
    "required": ["deployment", "namespace"]
  }
}

Resources — user-selected, read-only

A resource is a piece of data addressable by URI. The host or user picks it (“attach this file”, “include this runbook”) and the model reads it. No side effects, no input schema, just content. A server that wants to be a good citizen for reading files, docs, or read-only DB views exposes them as resources rather than tools. 

runbooks://incidents/db-outage.md
manifests://prod/deployment/payments.yaml

Prompts — user-invoked templates

A prompt is a named, parameterised message template that the user triggers, typically through a slash menu in the host. The server returns structured messages that the host injects into the conversation. Prompts let server authors ship reusable workflows without the model having to discover them.

Everything else

Three more primitives exist and you’ll meet them in advanced deployments; they aren’t the core of most servers:

  • Sampling — server asks the host to run an LLM completion on its behalf (so the server doesn’t carry its own model).
  • Roots — host declares which filesystem or workspace boundaries the server may operate within.
  • Elicitation — server pauses a tool call to ask the user a structured follow-up question.
In ClusterOps
  • Tools: list_pods, get_logs, restart_deployment, scale_deployment. All four are schema-validated and the host gates them behind an “approve?” prompt for anything write-shaped.
  • Resources: the incident runbook library (runbooks://…) and frozen copies of prod manifests (manifests://…). An SRE can drop a runbook into the chat to anchor the LLM’s reasoning before any tool fires.
  • Prompts: prompts/triage — takes severity, service, and owner and returns a pre-filled incident triage message, so every SRE starts from the same checklist.
  • ClusterOps does not use sampling or elicitation. Roots are irrelevant (no filesystem access).

4. Transports

The protocol layer (JSON-RPC 2.0, described in §5) is the same whatever channel it rides on. The transport is that channel. MCP defines two production transports plus a legacy one you’ll occasionally bump into.

stdio — local subprocess

The host launches the server as a child process and speaks JSON-RPC over stdin / stdout. One request per newline, stderr reserved for logs. There is no network, no authentication, no multi-tenancy: the OS user who ran the host is the authenticated identity, and each host gets its own subprocess.

Streamable HTTP — the current remote standard

Introduced in the 2025-03-26 revision and now the default for remote servers. A single HTTP endpoint (usually /mcp) accepts POSTs carrying JSON-RPC requests. For server-to-client pushes (progress notifications, sampling requests), the same endpoint can upgrade the response into a Server-Sent Events stream. State between calls is carried by an opaque Mcp-Session-Id header the server issues on initialize.

HTTP+SSE — legacy, deprecated

The original remote transport (pre-2025-03-26) used two separate endpoints — POST /messages for client requests and GET /sse for a long-lived server-sent-events channel. Deprecated and superseded by Streamable HTTP. You shouldn’t deploy a new server on it; you may need to bridge clients that only speak it.

Picking one

Factor stdio Streamable HTTP
Audience Single user on this machine Multi-user or remote
Auth OS user = identity, no extra auth OAuth 2.1 (see §9)
Scaling One subprocess per host Horizontal; session affinity needed
Typical use Filesystem, git, local DB dump Internal platform tools, SaaS APIs
In ClusterOps

Thirty SREs share one ClusterOps instance, so stdio is a non-starter — you’d have to ship kubeconfig to every laptop and give each SRE their own copy of the server process. ClusterOps runs as a Deployment behind a ClusterIP Service inside the cluster and speaks Streamable HTTP on /mcp. The gateway in front of it (see §8) handles OAuth before any JSON-RPC traffic reaches ClusterOps itself.

In the wild

Anthropic’s reference filesystem, git, and sqlite servers are stdio — they operate on local state that already belongs to the OS user. Cloudflare’s hosted MCPs and GitHub’s remote MCP server are all Streamable HTTP, because sharing them across users is the whole point.

5. JSON-RPC 2.0 & the lifecycle

Every MCP message is JSON-RPC 2.0. Three shapes, one per role: request (has id, expects a response), response (echoes the same id, carries result or error), and notification (no id, fire-and-forget). 

// request
{"jsonrpc":"2.0","id":42,"method":"tools/call","params":{...}}

// success response
{"jsonrpc":"2.0","id":42,"result":{...}}

// error response
{"jsonrpc":"2.0","id":42,"error":{"code":-32602,"message":"Invalid params"}}

// notification (no id, no reply)
{"jsonrpc":"2.0","method":"notifications/progress","params":{...}}

The lifecycle

A session has three phases: initialize, operate, shut down. The first one is where capability negotiation happens — neither side advertises anything before it, neither side assumes anything after.

Capability negotiation

In the initialize request the client advertises what it can do for the server (e.g. sampling); the server advertises what it exposes (tools, resources, prompts, …). Each side must not use a feature the other didn’t advertise. This is also where both sides agree on the protocolVersion.

In ClusterOps

The SRE’s client sends (abbreviated): 

{
  "jsonrpc": "2.0", "id": 1, "method": "initialize",
  "params": {
    "protocolVersion": "2025-11-25",
    "capabilities": { "sampling": {}, "roots": { "listChanged": true } },
    "clientInfo": { "name": "bank-internal-chat", "version": "1.4.0" }
  }
}

ClusterOps responds:

{
  "jsonrpc": "2.0", "id": 1,
  "result": {
    "protocolVersion": "2025-11-25",
    "capabilities": {
      "tools":     { "listChanged": true },
      "resources": { "subscribe": false, "listChanged": true },
      "prompts":   { "listChanged": false }
    },
    "serverInfo": { "name": "clusterops", "version": "0.9.2" }
  }
}

No sampling, no roots, no elicitation on the server side — ClusterOps is deliberately conservative.

6. A full tool-call walkthrough

The earlier segments named the pieces. This one walks them in motion: what actually happens, in order, from the moment an SRE types a question to the moment a plain-English reply lands back in the chat. The story has six phases. None of them involve JSON you need to memorise — they’re about who does what and why.

The scenario

Payments latency has spiked. The on-call SRE types into the chat:

“Payments is slow. Restart the payments deployment in prod.”

The SRE knows nothing about kube-apiserver APIs. The LLM knows nothing about this particular Kubernetes cluster. ClusterOps knows nothing about the SRE. Watch how those gaps close.

Phase 1 Discovery — the server hands over a catalog

Right after the initialize handshake (§5), the MCP client asks the server one question: “what can you do?” It sends a tools/list request, and the server replies with its catalog. Every tool shows up with three fields:

  • A name — the identifier the model later uses to invoke it (restart_deployment).
  • A description — a sentence or two of plain English explaining what the tool does and when to reach for it.
  • An input schema — JSON Schema for the arguments, so both client and server can validate before anything ships.

This catalog is the only thing the host will show the LLM about ClusterOps. It is, literally, the entire product surface. For this session it looks roughly like: 

Tools available from ClusterOps:

  list_pods(namespace)
    Return pods in a namespace with phase and restart count.
    Use when the SRE wants to see what's running.

  get_logs(pod, namespace, tail_lines?)
    Return recent log lines from a pod's main container.
    Use when investigating an error or a slowdown.

  restart_deployment(deployment, namespace)
    Perform a rolling restart of a Deployment by bumping its
    pod template annotation. Use when a service needs to be
    cycled cleanly (after a config change, to clear a stuck
    state, or as a recovery step).

  scale_deployment(deployment, namespace, replicas)
    Change the desired replica count for a Deployment.
    Use when adjusting capacity under load.

The client stashes this list; it will hand it to the LLM on every turn.

Phase 2 Comprehension — descriptions are the interface

This is the subtle part and it is the single most important thing to internalise about MCP. The LLM does not read source code. It does not know what a Deployment is or how kube-apiserver works. It reads those descriptions the same way you’d read a tool’s README.

A description that says “Perform a rolling restart of a Deployment… Use when a service needs to be cycled cleanly” teaches the model when restart_deployment is the right answer. A description that says “restarts things” gives the model nothing and it will guess. Writing good tool descriptions is the MCP server author’s primary job — they’re API docs for a reader whose only language is English, because that is exactly what the LLM is.

Rule of thumb

Every description should answer two questions: what does this do? and under what circumstances should the model prefer it over the other tools? The second half is where most server authors skimp and most tool misuse comes from.

Phase 3 Decision — intent becomes a proposed call

With the catalog loaded, the LLM takes the SRE’s natural language (“restart the payments deployment in prod”) and compares it against every tool description it was given. It concludes: the match is restart_deployment, with arguments {deployment: "payments", namespace: "prod"}. It validates those arguments against the input schema it was handed in phase 1 before producing them.

At this instant the LLM has produced a proposed tool call. Nothing has left the host yet. Nothing has touched the cluster. The LLM cannot act on its own — it can only hand the proposal to the host and ask to proceed.

Phase 4 Approval — the host is the gatekeeper

The host sees the proposed call and applies policy. For a read-only call (list_pods, get_logs), policy may auto-approve. For anything side-effectful — anything that mutates cluster state — it shows the SRE the exact call it’s about to make and waits for a yes.

Critically, this gate sits in the host, not the server. The server will happily execute whatever it receives once auth is satisfied. The responsibility for “should we actually do this?” lives with the human-facing component, because the host is the only part of the system that can show the SRE a prompt and get a click back.

Phase 5 Execution — the server touches the real service

Approved, the client sends tools/call with the name and arguments across the transport (§4). The ClusterOps server is the only component in the whole chain that holds the in-cluster kubeconfig and the only one that can speak to kube-apiserver. It revalidates the arguments against the schema, issues the real Kubernetes API call — here, a PATCH on the Deployment that bumps a pod-template annotation — and receives the actual outcome.

This is the only layer where the abstract “call a tool” becomes a concrete side effect on the cluster. It’s also the layer where audit logging should happen: who called what, with which arguments, against which target (§11).

Phase 6 Explanation — back to natural language

The server wraps the Kubernetes outcome into MCP’s result format — a small block of content items, each of type text or structured data — and ships it back. The host hands that to the LLM, which composes a reply in the voice of the conversation so far: “Restarted payments in prod; the rollout is in progress and new pods are coming up.”

The SRE reads that sentence. They never see the JSON request, they never see the HTTP path, they never see the schema. Everything the protocol did is hidden behind one round-trip of plain conversation. That is the whole value of MCP in a nutshell.

In ClusterOps

Between phases 5 and 6, the server’s actual work is one call to the Kubernetes API — the MCP equivalent of kubectl rollout restart deployment/payments -n prod. That is all. The whole protocol dance exists so the SRE doesn’t have to remember exact kubectl syntax under pressure, so the model reaches for the right action automatically, and so the audit trail captures who asked for what against a real user identity (see §9).

For the curious — what the wire actually carries

Everything above happens at the conceptual layer. Here’s what the bytes look like for phase 5’s request:

Authorization: Bearer eyJhbGciOi...
Mcp-Session-Id: 9f0e8d7c-4b2a-41e7-9ae4-1c3f0b2d5a68
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "tools/call",
  "params": {
    "name": "restart_deployment",
    "arguments": { "deployment": "payments", "namespace": "prod" }
  }
}

And phase 6’s response back to the client:

HTTP/1.1 200 OK
Content-Type: application/json

{
  "jsonrpc": "2.0",
  "id": 42,
  "result": {
    "content": [
      { "type": "text",
        "text": "Rolled out deployments/payments in namespace prod. generation: 38" }
    ],
    "isError": false
  }
}

id: 42 matches across request and response. That is how the client pairs a reply with the request that triggered it, and it’s why structured logs keyed on JSON-RPC id are such a good audit substrate (see §11).

7. Build your first MCP

You’ve read the theory; let’s prove it with about 35 lines of Python. This section builds a complete, working MCP server that exposes one tool — disk_usage(path) — and walks that tool through the six phases from §6.

Why disk_usage? Every infrastructure engineer has typed du -sh /var/log at 2am. It’s pure local, needs no auth, has zero external dependencies, and the description you have to write for it forces the key lesson from §6: the LLM picks tools by reading descriptions, so the description is the interface.

The 35 lines

We use FastMCP from the official Python mcp SDK. It handles the JSON-RPC loop, schema generation from type hints, and the stdio transport so you can focus on the tool itself. 

import subprocess
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("disk-usage")                               # 1

@mcp.tool()                                                # 2
def disk_usage(path: str) -> str:                          # 3
    """Return the total disk usage of a directory as a human-readable string.

    Use when the user wants to know how much space a directory occupies,
    for instance before deleting, archiving, or diagnosing disk pressure.
    Works on any path readable by the current user. Returns a string
    like "1.4G\t/var/log"; reports an error message if the path is
    unreadable or does not exist.
    """                                                    # 4
    try:
        result = subprocess.run(
            ["du", "-sh", path],
            capture_output=True, text=True, timeout=30, check=True,
        )
        return result.stdout.strip()
    except subprocess.CalledProcessError as e:
        return f"du failed: {e.stderr.strip()}"
    except FileNotFoundError:
        return f"Path not found: {path}"

if __name__ == "__main__":
    mcp.run()                                              # 5
What each marked line does
  1. FastMCP("disk-usage") — creates the server. The name is what clients see in initialize responses (§5).
  2. @mcp.tool() — registers the function in the server’s tool list. This is what tools/list will return to the client during discovery (§6 phase 1).
  3. Type hints — path: str becomes the tool’s input JSON schema ({ "type": "object", "properties": { "path": { "type": "string" } } }). The SDK introspects the signature so you never hand-write schema.
  4. The docstring — this is the description the LLM reads to decide whether to call your tool. Write it for the model, not for another developer. State when to use it, not how it’s implemented. This is §6 phase 2 (Comprehension) in concrete form.
  5. mcp.run() — starts the stdio JSON-RPC loop. Reads requests from stdin, writes responses to stdout, keeps stderr free for logs. This is how your script “speaks MCP” (§4 Transports).

Your 35 lines in the MCP picture

Wire it to a host

A host like Claude Desktop spawns MCP servers by reading a JSON config. It runs your script as a subprocess and pipes JSON-RPC through stdin/stdout. The config looks like this: 

{
  "mcpServers": {
    "disk-usage": {
      "command": "python",
      "args": ["/absolute/path/to/your_server.py"]
    }
  }
}

Drop that in the host’s MCP config file, restart the host, and your tool shows up. The host handles discovery; you don’t wire anything up by hand.

Trace it through §6’s six phases

Every phase from the tool-call walkthrough maps onto a concrete piece of this code:

  • 1. Discovery — host calls tools/list; FastMCP answers with every function decorated by @mcp.tool().
  • 2. Comprehension — the model reads your docstring to decide when disk_usage is the right tool. This is the most important line you write.
  • 3. Decision — the model emits a tools/call with { "name": "disk_usage", "arguments": { "path": "/var/log" } }. Argument shape comes from your type hints.
  • 4. Approval — the host asks the user to confirm before forwarding the call (Claude Desktop will prompt). Your code runs only after the user says yes.
  • 5. Execution — subprocess.run(["du", "-sh", path]) is the side effect. This is where the abstract call becomes a real read on the filesystem.
  • 6. Explanation — your return string goes back as the tool result; the model turns 1.4G\t/var/log into “/var/log is using 1.4 GB.”

Extensions

Try these without looking at solutions. Each one stretches a different part of the protocol:

  • Add a free_space(mount: str) tool that shells out to df -h. Notice you get a second tool with its own schema for free.
  • Expose /etc/fstab as a resource (not a tool) under the URI fstab://local. Resources are pulled on demand instead of invoked — see §3.
  • Add a cleanup_audit prompt the user can invoke from the host’s prompt menu, which pre-populates the model with “walk these paths, report the top 5 largest directories, suggest safe deletions.”
  • Swap mcp.run() for mcp.run(transport="streamable-http", port=8080). Your tool is now a remote MCP — one change, no other edits. This is the seam ClusterOps uses in production.
In ClusterOps

ClusterOps is this exact skeleton. Swap subprocess.run(["du", ...]) for the Kubernetes Python client, swap mcp.run() for a Streamable HTTP transport behind a gateway, and add OAuth at the edge (§9). The MCP-specific code — FastMCP, @mcp.tool(), docstrings, type hints — stays exactly the same. The protocol is not what grows; your integrations and your deployment story are.

In the wild

Anthropic’s mcp-server-filesystem is the full-featured cousin of the server above. It exposes read, write, list, search, and move tools over a sandboxed root directory and is the reference implementation most new MCP authors read first. The shape — decorated functions, SDK-generated schemas, stdio transport — is identical to what you just wrote.

8. Deployment topologies

Once you have a working MCP server, where do you put it? The protocol itself is transport-agnostic, but the deployment shape — local subprocess, remote HTTP service, or a gateway fronting many servers — determines your blast radius, your scaling story, and your audit surface. Three topologies cover almost every real deployment.

Topology A — local stdio

The host spawns the server as a child process on the same machine and speaks JSON-RPC over stdin/stdout. No network, no auth, no multi-tenancy. The OS user is the identity. This is where your disk_usage server from §7 lives, and where Anthropic’s filesystem and git MCPs live by default.

Good fit when: the tool needs resources only the laptop has (local files, local kubeconfig, an IDE’s open buffers), or you’re iterating on a tool and don’t want to stand up infrastructure for it.

Topology B — remote HTTP, one server per tool domain

The server runs as a long-lived HTTP service, reachable at a single /mcp endpoint over Streamable HTTP. Clients across many laptops share it. Auth happens per-request (§9). This is ClusterOps as a single Deployment behind a ClusterIP.

Good fit when: the underlying integration needs credentials that shouldn’t leave the datacenter (a kubeconfig with cluster-admin, a database password, a Jira API token), or the tool needs to be updated centrally rather than re-shipped to every laptop.

Topology C — gateway / federation

A gateway sits in front of many MCP servers and exposes them to clients as one endpoint. It handles TLS, OAuth, rate limiting, routing, and audit in one place; the MCP servers behind it stay small and focused. This is the pattern every larger-than-toy deployment converges on.

Good fit when: you have more than one MCP server, more than a handful of users, or any requirement that says “auth and audit have to live in one place.” In practice that is every enterprise deployment.

In ClusterOps

ClusterOps started as Topology B — one pod, one /mcp endpoint, OAuth baked into the server itself. Six months later the platform team added a postgres-readonly MCP and a jira MCP, and suddenly there were three OAuth integrations and three sets of audit log shipping to maintain. The fix was Topology C: deploy a gateway (they used ContextForge-style federation), move OAuth to the edge, and let ClusterOps drop its auth code entirely. The gateway advertises all three servers’ tools to clients under one endpoint.

In the wild

Cloudflare’s hosted remote-MCP offering is Topology B at SaaS scale: one public endpoint per product (Workers, R2, D1), each speaking Streamable HTTP. Enterprises that run >5 MCP servers almost universally put an API gateway or a dedicated MCP gateway (MCP-Gateway, ContextForge) in front — Topology C — because otherwise every server grows its own parallel copy of auth, logging, and rate-limiting code.

9. Authorization

The moment an MCP server leaves a single laptop, you need to answer two questions on every request: who is this? and what are they allowed to do? MCP’s answer is OAuth 2.1 with PKCE — the same flow browsers and mobile apps use — plus a small amount of MCP-specific discovery so clients can find the right authorization server without any hard-coded config.

The three MCP-specific pieces on top of OAuth 2.1

OAuth 2.1 gives you the bulk of the machinery. MCP adds three conventions on top so a client that has never talked to your server before can still complete the flow:

  1. WWW-Authenticate on 401 — an unauth’d request to /mcp returns HTTP 401 with a WWW-Authenticate header pointing the client at the resource metadata document.
  2. /.well-known/oauth-protected-resource — a JSON document at the resource’s origin that lists the authorization server the client should use and the scopes this resource accepts. The client reads this and then hands off to OAuth.
  3. Dynamic Client Registration (DCR) — the client can register itself with the authorization server at first contact (RFC 7591), so there’s no “paste this client_id into your config” step. Many enterprise deployments disable DCR and pre-provision clients, which is fine — it’s an option, not a requirement.

The flow, end to end

Scopes and token shape

Tokens are opaque bearer tokens (or JWTs — MCP doesn’t prescribe). The scopes in the token decide which tools the user can call. A common split for a server like ClusterOps is one scope per risk tier: 

clusterops.read    → list_pods, get_logs, describe_*
clusterops.write   → restart_deployment, scale_deployment
clusterops.admin   → delete_*, drain_node, cordon_node

The server enforces scopes on each tools/call. A tools/list response can also be filtered by scope, so a junior SRE simply doesn’t see tools they can’t use — which is both a safety property and a UX win (the model won’t try to call a tool it never learned about).

In ClusterOps

ClusterOps’s gateway is configured so an unauth’d POST /mcp returns 401 with a WWW-Authenticate pointing at https://clusterops.internal.bank/.well-known/oauth-protected-resource. That document names the bank’s internal Keycloak realm as the authorization server. Access tokens are JWTs signed by Keycloak; the gateway verifies the signature, extracts scope and sub, and forwards them to ClusterOps as trusted headers. A junior SRE’s token carries clusterops.read only — they can ask the model to investigate, but restart_deployment simply doesn’t appear in tools/list. A senior SRE’s token carries clusterops.write and sees the full toolset.

Two easy mistakes
  • Audience confusion. A token issued for MCP server A must not be accepted by MCP server B. Always check the aud claim (or resource indicator) on validation.
  • Token passthrough. The model must never see or reason about the access token itself. It belongs to the host/client and the server, not to the sampling loop.

10. Airgapped deployments

Nothing in MCP assumes the public internet. The protocol is transport-agnostic, the auth story uses your authorization server, and servers can be pulled from a local registry. What airgapped deployment actually requires is the discipline to name every external dependency your server has and mirror it inside the perimeter. Here’s the list, and the topology that falls out of it.

What needs to move inside the perimeter

External dependency Airgapped replacement
Public container registries (Docker Hub, GHCR) Internal registry (Harbor, Artifactory, ECR on-prem)
Public MCP registry at registry.modelcontextprotocol.io Seeded internal registry; point clients via MCP_REGISTRY_SEED_FROM=https://mcp.internal/registry.json
Public OAuth providers (Auth0, Okta Cloud) Internal IdP (Keycloak, on-prem Okta, AD FS)
Model APIs (api.anthropic.com, OpenAI) On-prem inference (vLLM, TGI, internal gateway) or a model running in the same VPC
Secrets in environment variables Vault / sealed-secrets with short-lived leases
Public PyPI / npm Internal mirror (devpi, Verdaccio, Nexus)
Outbound DNS / NTP Internal resolvers, internal NTP; egress NetworkPolicy: deny-all

The resulting topology

The registry seed

MCP clients discover servers through an MCP registry. In an airgapped build you don’t want clients reaching for registry.modelcontextprotocol.io. Seed an internal registry from a static manifest baked into the cluster: 

# env for the MCP host / client
MCP_REGISTRY_SEED_FROM=https://mcp.internal.bank/registry.json
MCP_REGISTRY_DISABLE_PUBLIC=true

The manifest is a plain list of servers, their endpoints, and their advertised capabilities. Platform engineers own it the same way they own a Helm chart repo.

Zero-egress network policy

The cheapest proof that a deployment is airgapped is a default-deny egress policy. In Kubernetes: 

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: mcp-no-egress
  namespace: clusterops
spec:
  podSelector: { matchLabels: { app: clusterops-mcp } }
  policyTypes: [Egress]
  egress:
  - to:
    - namespaceSelector: { matchLabels: { name: kube-system } }   # apiserver
    - namespaceSelector: { matchLabels: { name: platform-auth } } # Keycloak
    - namespaceSelector: { matchLabels: { name: platform-vault } }
    ports:
    - { protocol: TCP, port: 443 }

If ClusterOps needs anything the policy doesn’t list, the connection fails closed. That’s the whole point. Any new dependency becomes a visible review step, not a silent call to the public internet.

In ClusterOps

Everything the bank’s SREs touch lives inside one VPC. Laptops reach an internal chat UI; the chat UI reaches an internal LLM runtime; the LLM acts as the MCP client and talks to the gateway; the gateway verifies Keycloak-signed JWTs and forwards to ClusterOps; ClusterOps talks to the kube-apiserver of the same cluster it runs in. No DNS query ever leaves. The weekly security scan’s egress-flow report shows a flat zero outside the VPC — which is what the bank’s regulator actually asks for.

In the wild

Anthropic publishes an offline-ready Docker image of its reference MCP servers so regulated customers can mirror them into internal registries without ever pulling from Docker Hub at runtime. Similar patterns exist for the filesystem, git, and Postgres reference servers — the source code is public, and the build artifact is designed to be mirrored.

11. Operations & scaling

A working MCP server is easy. An operable MCP server — one you can debug at 2am, scale with load, and answer compliance questions about — comes from four habits you bake in on day one: session affinity, horizontal scaling that respects it, structured logs keyed on the JSON-RPC id, and an audit trail your security team actually wants to read.

Session affinity

Streamable HTTP clients hold a logical session across many POST /mcp requests. The Mcp-Session-Id header (issued by the server on initialize) identifies which replica “owns” that session — the one holding the negotiated capabilities, any resource subscriptions, and the SSE stream for server-initiated messages. Break affinity mid-session and the client sees its in-flight calls vanish.

In practice: set your gateway or Service to consistent-hash on Mcp-Session-Id (or on the bearer-token subject as a fallback). Plain round-robin breaks Streamable HTTP; cookie-based stickiness also works but is less precise than hashing the explicit session header.

Horizontal scaling

With affinity in place, scaling is ordinary: run N replicas behind the gateway, let sessions land on whichever replica hashes to their ID, and drain replicas by refusing new sessions (503 on initialize) while letting existing ones complete. Sessions are short enough — minutes to hours — that rolling deploys finish within a normal window. No shared state between replicas is required if each session is pinned to one.

Structured logs keyed on JSON-RPC id

Every MCP request except notifications carries a numeric id. Log one line per request, one line per response, both tagged with that id. You can now correlate across a whole tool call — the tools/call request, the response, any notifications/progress in between — without trying to reconstruct sessions from timestamps. A minimal log line looks like: 

{
  "ts": "2026-04-19T14:22:01.488Z",
  "level": "info",
  "event": "tools.call.request",
  "session": "9f0e8d7c-4b2a-41e7-9ae4-1c3f0b2d5a68",
  "jsonrpc_id": 42,
  "sub": "sre_jane",
  "tool": "restart_deployment",
  "args": { "deployment": "payments", "namespace": "prod" }
}

Audit trail

The audit trail is a thin projection of those logs aimed at humans who will never read raw JSON. Write one row per tools/call with the fields your compliance team actually needs: 

user_sub · tool_name · arguments · target · outcome · ts · jsonrpc_id

The jsonrpc_id is the bridge from audit back to raw logs if anyone needs the full wire trace of an incident. Keep audit rows immutable and append-only; keep raw logs rotatable.

2026 roadmap caveats

  • Streaming tool results are first-class in spec 2025-11-25; long-running tools should emit notifications/progress rather than block a single response.
  • Elicitation (server asks the user a follow-up question mid-call) is stable; expect hosts to surface it as native UI over the coming year.
  • Transport evolution: legacy HTTP+SSE is deprecated but still widely deployed; plan a migration window to Streamable HTTP before retiring clients that only speak the old transport.
In ClusterOps

ClusterOps runs five replicas behind the gateway. The gateway consistent-hashes on Mcp-Session-Id so an SRE’s session stays pinned for its lifetime. Every tools/call writes both a structured log (event: tools.call.request, keyed by session and jsonrpc_id) and an audit row (user_sub + tool_name + deployment + outcome). When last week’s post-incident review asked “who restarted payments at 03:47?”, the answer came from one grep against the audit table — and the full wire trace came from joining that row’s jsonrpc_id back to the raw log stream.

12. Capstone scenario

Time to put it all together. The bank’s dev-platform team has asked you to add a new MCP to the internal stack. Use everything from §1–§11 to make the design calls.

The ask

Add a code-search MCP for the ~500 dev-platform engineers at the same airgapped bank. It exposes two tools against the bank’s internal monorepo index:

  • search(query, repos?) — grep-style search across indexed repos
  • get_file(path, revision?) — fetch file contents at a revision

Constraints: reuse ClusterOps’s gateway, reuse the bank’s Keycloak; no new external dependencies; same airgapped VPC; must scale to 500 users.

Pick the answer you would defend in a design review, then reveal the recommendation.

Design call yourself

Five questions. There’s one best answer per question, but partial credit is fine — the explanations explain the trade-offs.

1. Transport?
2. Deployment placement?
3. Auth scopes?
4. How do clients discover it?
5. Biggest failure mode to design against?
The shape to build

One Deployment of the code-search MCP on Streamable HTTP, registered as a fourth backend on the existing gateway. Keycloak issues tokens with two scopes (code-search.read, code-search.fetch); the gateway verifies and forwards. The seeded internal MCP registry gains one new entry. Every get_file call logs path + revision to the audit trail, keyed by JSON-RPC id (§11). Horizontally scale the backend with consistent-hash session affinity, same pattern as ClusterOps. Zero new external dependencies — the whole deployment stays inside the VPC.

What you did not need to invent. No new transport. No new auth system. No new client-side config distribution. No new audit pipeline. That’s the payoff of the protocol plus the gateway plus the registry: the fifth MCP you add looks almost exactly like the fourth, and the fifteenth will look like the fifth.
